# Задание агенту: учебный сайт-учебник на GitHub Pages и система агентов для его разработки

Ты главный агент (оркестратор). Прочитай план целиком, затем действуй в порядке из раздела 1.

## 0. Что строим

Репозиторий на GitHub с сайтом на GitHub Pages. Сайт устроен как набор учебников по темам. Каждая страница объясняет материал с интерактивными графиками, визуализациями и запускаемым кодом. Тексты качественные и сжатые, без воды, со структурой.

Темы (каждая отдельный учебник с главами):
- **DL Theory**: формулы и теория методов, с объяснением.
- **Classic ML**: теория для подготовки к собеседованиям.
- **MLOps Practices**: разборы методов улучшения архитектуры.
- **CompScience**: теория вычислений, алгоритмы, оптимизации на уровне железа.
- **Compute**: разборы CUDA, Triton и подобного; понятные юзкейсы и ситуации, когда это нужно применять.

Проект должен легко масштабироваться: новая тема или глава добавляется без правки ядра. Код пишется чисто и грамотно. Тесты только на важный функционал, coverage не цель. ESLint, Prettier, ruff подключить, это недорого.

## 1. Порядок работы

1. **Изучи референсы** (открой живые сайты и репозитории, выпиши визуальный язык в `docs/design-system.md`):
   - Transformer Explainer: https://poloclub.github.io/transformer-explainer/ , репозиторий https://github.com/poloclub/transformer-explainer (MIT; SvelteKit + Vite + TypeScript + Tailwind + D3). Берём: обзор сверху и детали по запросу, плавные переходы между уровнями абстракции, пошаговые карточки «guided learning», живой интерактив.
   - MLU-Explain: https://mlu-explain.github.io/ . Берём: единообразные визуальные эссе, скролл-повествование, живые примеры внутри текста. Репозиторий https://github.com/mlu-explain/mlu-explain.github.io содержит только собранный статический сайт (папка на статью) и явной лицензии не показывает. Структуру репозитория не копируем, файлы и шрифты не копируем. Берём только впечатление и принципы вёрстки, всё пишем сами.
   - Interactive Primer: https://interactiveprimer.com/ . Берём только: интерактивные запускаемые блоки кода, общее оформление страниц (карточки, врезки «Watch out!» про типичные ошибки, сворачиваемые отступления), единый набор компонентов и тема на токенах, граф пререквизитов между главами. **Не берём**: самооценку знаний и «уверенность» по понятиям, диагностические тесты, вопросы о навыках и желаемых результатах, рекомендатель «что дальше».
   - Для вдохновения по приёмам: Red Blob Games (подсветка элемента в тексте и на диаграмме одновременно, объяснения «изнутри»), Bartosz Ciechanowski (ссылки в тексте, которые переводят демо в нужное состояние; слова в тексте, цветом связанные с элементами демо; переключатель реального и увеличенного масштаба), Distill (формат длинной статьи).
2. **Задай мне вопросы** через AskUserQuestion по пунктам из раздела 9 (не больше 4 вопросов за раз, рекомендуемый вариант первым). Не начинай реализацию, пока не получишь ответы на критичные.
3. **Подготовь основу** (всё, что нужно агентам для работы): `CLAUDE.md`, `.claude/agents/*.md`, `docs/ARCHITECTURE.md`, `docs/design-system.md`, `docs/CONTENT-GUIDE.md`, шаблоны задач (раздел 8).
4. **Контракты сначала.** До параллельной работы зафиксируй интерфейсы: схемы данных (Zod), API компонентов, форматы файлов, заглушки модулей. Субагенты пишут код против контрактов.
5. **Вертикальный срез**: одна тема, одна глава, один лаб, оба слайдера, поиск, заметки, прогресс, деплой на Pages. Только после работающего среза масштабируй контент.

## 2. Технологический стек (по умолчанию, можно оспорить с обоснованием)

- SvelteKit + `adapter-static` + TypeScript + Vite + Tailwind + D3. Это стек Transformer Explainer, подходит под нужное нам оформление.
- Главы: Markdown с Svelte-компонентами (mdsvex). Формулы: KaTeX на этапе сборки.
- Редактор кода в браузере: CodeMirror 6.
- Python в браузере: Pyodide в Web Worker с таймаутом (принудительный terminate), без сети. PyTorch в Pyodide, насколько известно, недоступен (проверь актуальный статус). Поэтому DL-лабы по умолчанию на NumPy или JS/TS. Там, где нужен torch, используется отдельный механизм (раздел 9, вопрос 4).
- Поиск по содержимому: Pagefind (полнотекстовый, статический, работает на Pages).
- Графики: общая библиотека обёрток над D3 с темой на токенах (светлая/тёмная, `prefers-reduced-motion`).
- Python-инструменты репозитория (проверки лабов, скрипты): ruff.
- CI на GitHub Actions: проверки → сборка → деплой на Pages. Базовый путь `/<repo>`.

## 3. Структура репозитория (ориентир)

```
CLAUDE.md
docs/                      ARCHITECTURE, design-system, CONTENT-GUIDE, LANES
tasks/                     пакеты работ, claims/, отчёты
src/lib/                   компоненты, движок глубины, поиск, лабы, заметки, прогресс
src/routes/                тонкие маршруты, контент подключается автоматически
content/<topic>/<chapter>/ index.svx + meta (frontmatter по схеме) + labs/
labs/<lab-id>/             starter, tests, reference solution, lab.yaml
scripts/                   проверка контента, генерация реестров, пакет заметок для агента
tests/                     немного, на важное
user-data/                 заметки, прогресс, черновики; НЕ публикуется (раздел 6)
```

Реестры тем и глав генерируются сканированием папок (glob), а не правятся вручную. Тогда параллельные агенты не конфликтуют на общих файлах.

## 4. Контент и стиль

- Каждая глава в frontmatter: стабильный `id`, название, пререквизиты (граф зависимостей между главами и понятиями), ключевые слова, оценка времени, список лабов, источники.
- Скелет раздела: идея (1–2 предложения) → интуиция → математика → код → частые ошибки → проверь себя. Без воды. Таблицы, графики, списки, структура приветствуются.
- Интерактив только там, где он объясняет то, что статика не передаёт. Каждый интерактив имеет подпись и текстовую альтернативу.
- Приёмы: текст и график связаны подсветкой; слова в тексте ведут к состоянию демо; пошаговые карточки на сложных схемах; параметризованные вопросы для самопроверки (по желанию, не оценка навыков); для Classic ML отдельный режим вопросов собеседования.
- Числа и факты про железо и API подтверждаются документацией; источники в `meta`. Отдельный проход проверки фактов субагентом, не писавшим текст.
- Единый словарь терминов (глоссарий) с подсказками при наведении.

## 5. Слайдеры сложности и глубины

Сверху страницы два слайдера по 3–5 положений:
- **Сложность** (для кого объяснение).
- **Глубина деталей реализации и железа**.

После перемещения слайдера появляется кнопка «Применить». Текст меняется только по нажатию. Выбор сохраняется (раздел 6) и попадает в URL.

Технически: никакой генерации в рантайме, всё компилируется при сборке. Предложи мне варианты через AskUserQuestion (раздел 9, вопрос 1) и покажи на примере одного реального раздела, как отличается текст. Рекомендуемый вариант: аддитивные слои, где каждый блок помечен минимальным уровнем по каждой оси, плюс замена отдельных блоков там, где нужна иная подача. Полные параллельные переписывания по уровням не берём: при 5×5 положениях это до 25 версий каждого раздела.
Скрипт проверки контента гарантирует, что на любом уровне нет ссылок на термины, определённые только в более глубоких слоях. Поиск индексирует все слои.

## 6. Пользовательские данные: заметки, прогресс, черновики

Всё это живёт отдельно от публичного контента в `user-data/` с понятными путями и версионированной схемой. Сборка Pages не включает эту папку. Страницы публикуются из публичного репозитория, поэтому заметки и прогресс не должны попадать в публикуемый репозиторий. Решение по хранению через вопрос 2.

### Прогресс
- Сохраняется **автоматически**, без анкет и оценок: посещённые главы, дойдено ли до конца раздела, пройденные лабы (тесты зелёные), последняя позиция, выбранные положения слайдеров.
- Черновики кода в лабах сохраняются при редактировании и восстанавливаются при следующем открытии.
- Необязательная кнопка «отметить пройденным» на главе. Никаких звёзд, самооценки и рекомендаций, что учить дальше.
- Всё привязано к стабильным `id` глав и лабов. Если главу переименовали, помогает таблица алиасов. Если изменился стартовый код лаба, черновик не теряется, а показывается предупреждение.
- Интерфейс `ProgressStore` с адаптерами. Локальный по умолчанию (IndexedDB). Экспорт и импорт JSON. Синхронизация между устройствами через тот же механизм, что и заметки.
- Схема с версией и миграциями.

### Заметки на полях
- Выделяю строку, формулу или график и оставляю комментарий. Формат якоря в духе W3C Web Annotation: `id` блока (стабильный, задаётся автором и проверяется линтером) + цитата с контекстом (`exact`, `prefix`, `suffix`) + для рисунков `figure_id` и элемент. Если текст изменился, якорь ищется по цитате; не нашёлся — заметка помечается «осиротевшей», но не теряется.
- Один файл на заметку: `user-data/notes/<topic>/<chapter>/<ulid>.json`. Так не бывает конфликтов слияния. Поля: якорь, текст, теги, статус (`open` / `answered`), время.
- Ответы агента: `<ulid>.answer.md` рядом.
- Взаимодействие с агентом: команда `notes pack --status open [--topic X]` собирает markdown-пакет (цитата + контекст главы + мой комментарий). Агент отвечает файлом, а правки в главу предлагает отдельным изменением на ревью, а не вносит молча. Предложи детали формата и покажи пример.

### Дизайн
- Воздушный и приятный глазу. Современный, как в Transformer-explainer.
- Темная тема с возможностью переключения (нужно посмотретЬ .что она адекватно выглядит)

## 7. Интерактивный код и обратная связь

- Блок кода редактируемый: меняю функцию, класс или метод, нажимаю «Запустить» и получаю результат прямо на сайте.
- Каждый лаб описан в `lab.yaml`: стартовый код, видимые и скрытые тесты, эталонное решение, визуализаторы результата.
- Результат запуска это структурированный JSON (`LabResult`): статус по тестам, диффы, метрики, временные ряды, массивы, время выполнения. Он рисуется общими компонентами графиков того же стиля, что и остальной сайт, а не картинками matplotlib. Фидбек понятный: что упало, где, какие значения ожидались, плюс графики (например, кривая обучения).
- CI проверяет каждый лаб: эталон проходит все тесты, стартовый код не проходит.
- Compute (CUDA, Triton): на Pages эти ядра не запускаются. Покажи варианты в вопросе 4.

## 8. Оркестрация: что должно быть в `CLAUDE.md`

Все эти правила пропиши в `CLAUDE.md` явно и коротко. Я буду запускать разные сессии: модель в них - оркестратор; она вызывает субагентов.

**Роль оркестратора.** Сам не пишет код, кроме правок конфигурации и интеграции. Он разбивает работу на пакеты, запускает субагентов, проверяет результат, объединяет. Сам читает результаты проверок, а не отчёты субагентов на веру.

**Субагенты.** Haiku 5.5 medium. Каждая задача рассчитана на меньше 100–140k токенов. Ориентир размера: одна задача, примерно до 10 файлов и около 600 строк изменений, одна забота (один компонент, один раздел главы, один лаб). Если субагент упирается в бюджет, хотя ему нужно еще очень много делать, он останавливается и возвращает частичный результат, а не расширяет задачу. Если надо доделать токенов 10к-20к, тогда пусть доделывает. Если пакет провален дважды: разбей мельче. Архитектуру, дизайн-систему и интеграцию делает оркестратор или субагент Sonnet 5.5 medium.

**Параллелизм без конфликтов.**
- Запускай много субагентов сразу, в фоне. Не жди простаивая: пока идут задачи, готовь следующие пакеты и проверяй завершённые. Не опрашивай в цикле, опирайся на уведомления о завершении.
- Каждая задача работает в своём git worktree и ветке. В описании задачи явный список файлов, которыми она владеет, и список запрещённых. Общие файлы (манифесты пакетов, lock-файл, маршруты, корневой конфиг) трогает только оркестратор. Реестры генерируются, а не правятся руками.
- Если двум задачам нужен один файл, раздели задачу или выстрой по порядку.
- Слияние по одному, в порядке зависимостей, после зелёных проверок, rebase перед слиянием.

**Пакет работ** (`tasks/<id>.md`): цель, контракты и интерфейсы, владеемые и запрещённые файлы, критерии приёмки в виде команд, бюджет, ссылки на примеры для копирования. Отчёт субагента в фиксированном формате до 200 слов: изменённые файлы, выполненные команды и результаты, открытые вопросы.

**Проверка.**
- Оркестратор сам запускает `check` (типы, линтер, тесты, проверка контента) по каждому пакету.
- Для визуальной части: скриншоты через Playwright, оценка отдельным проверяющим агентом, не писавшим код.
- Для контента: проверка фактов и согласованности уровней отдельным агентом.
- Для важных пакетов проверку делает агент, который не видел процесс написания.

**Несколько сессий параллельно.** Работа разделена на «дорожки» (например, платформа, DL, Classic ML, MLOps, CompScience, Compute, лабы). Закрепление за сессией в `docs/LANES.md`. Перед началом пакета сессия создаёт и пушит файл `tasks/claims/<id>.claim` (по файлу на заявку, без конфликтов) и сначала проверяет чужие. Каждая сессия работает в своих ветках и worktree.

**Тесты.** Vitest на ключевую логику (движок глубины, якоря заметок, хранилище прогресса, поиск, раннер лабов). Несколько Playwright-сценариев на критичные пути: страница открывается, «Применить» меняет текст, запуск лаба показывает результат, заметка создаётся, прогресс сохраняется и восстанавливается. Python-тесты для эталонов лабов. Тесты на каждый чих не пишем.

**Роли в `.claude/agents/`**: orchestrator, architect, component-dev, content-writer, lab-author, verifier, design-qa. Для каждой: когда использовать, что можно и нельзя трогать, формат отчёта. Добавь команды/навыки для повторяющихся процедур: новая глава, новый лаб.

## 9. Вопросы мне (через AskUserQuestion)
