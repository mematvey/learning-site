# Процедура: новый лаб

Вход: `lab-id` в формате `<topic>-<slug>` (например `dl-attention-numpy`), id главы, который он сопровождает, список функций и требуемое поведение, тип рантайма (раздел «Варианты» ниже). Правила идентификаторов: `CLAUDE.md`. Формат результата запуска (`LabResult`) и API раннера: `docs/ARCHITECTURE.md` (появится в срезе; до тех пор не придумываем свой формат, берём описанный там).

Процедура для оркестратора. Лаб пишет агент lab-author, один лаб на пакет.

## Шаг 0. Заявка

1. Worktree и ветка: `git worktree add -b task/lab-<lab-id> .worktrees/lab-<lab-id> main`.
2. `git pull`, проверить `tasks/claims/`, создать и запушить `tasks/claims/lab-<lab-id>.claim`.
3. Проверить, что `labs/<lab-id>/` ещё не существует.
4. Согласовать с главой: id главы в `labs` frontmatter, id блоков, на которые лаб ссылается в тексте «Код». Эти id фиксируются до написания лаба.

## Шаг 1. Структура

```
labs/<lab-id>/
  lab.yaml            описание: метаданные, рантайм, список тестов, визуализаторы
  starter.py          стартовый код для читателя (функции-заглушки)
  solution.py         эталонное решение (не показывается)
  tests_visible.py    тесты, видимые читателю
  tests_hidden.py     тесты, не показываются; проверяют края и устойчивость
```

Имена файлов фиксированные. Другие файлы в папке не кладём без причины; фикстуры для компонентов Compute (раздел «Варианты») лежат в `labs/<lab-id>/fixtures/`.

Пример `lab.yaml` (ориентировочный, схема уточнится в `ARCHITECTURE.md`):

```yaml
id: dl-attention-numpy
title: Scaled dot-product attention на NumPy
chapter: dl/attention
runtime: pyodide-numpy            # pyodide-numpy | simulator | external-notebook
entry: attention                  # функция, которую вызывают тесты
timeout_s: 10
tests:
  visible: tests_visible.py
  hidden: tests_hidden.py
visualizers:
  - weights-heatmap               # компоненты из src/lib, которыми рисуется LabResult
```

## Шаг 2. Файлы

**starter.py.** Функции с правильной сигнатурой, докстрингом (на английском) и телом `raise NotImplementedError`. Никаких подсказок в коде, которые раскрывают решение. Импорты только те, что нужны читателю.

**solution.py.** Чистое эталонное решение, читаемое, без трюков. Именно он проходит все тесты. Поведение совпадает с тем, что описано в тексте главы (тот же масштаб, те же оси).

**tests_visible.py.** Понятные проверки: форма выхода, маска, один-два маленьких ручных случая с ожидаемыми значениями. Сообщения об ошибках на английском, с ожидаемым и фактическим значением, например: `expected shape (4, 8), got (4, 4)`. Читатель должен понять, что упало и где, без подглядывания в решение.

**tests_hidden.py.** Края и устойчивость: `d = 1`, большой `d` (масштаб логитов), полностью замаскированная строка, нечисловые входы, численная стабильность softmax. Генераторы случайных чисел с фиксированным `seed`. Сообщения об ошибках не раскрывают скрытые ожидаемые значения: только общее «mismatch on random input, seed 0».

Правила для всех тестов:

- Детерминированы: одинаковый результат при каждом запуске.
- Допуски явные: `rtol`, `atol` в коде теста, одинаковые для эталона и читателя.
- Без сети, без файловой системы вне лаба, без зависимостей вне разрешённого набора (для Pyodide это NumPy и стандартная библиотека; точный список в `ARCHITECTURE.md`).
- Время выполнения в пределах `timeout_s` на эталоне с запасом в 3 раза.

## Шаг 3. Правило приёмки

Обязательное, проверяется CI (`lab-check`):

1. **Эталон проходит:** `solution.py` проходит все видимые и скрытые тесты.
2. **Старт не проходит:** `starter.py` падает хотя бы в одном тесте (он даёт `NotImplementedError` или неверный результат). Если старт проходит, лаб бесполезен: тесты не проверяют реализацию.
3. Лаб не зависит от случайных данных без `seed`. Повторный запуск даёт тот же `LabResult`.
4. Результат запуска соответствует `LabResult` (`ARCHITECTURE.md`): статус по каждому тесту, сообщение, диффы, метрики, массивы для визуализаторов.

Команды (появятся в срезе): `lab-check labs/<lab-id>` выполняет пункты 1–4. `uv run ruff check labs/<lab-id>` для Python-файлов. До среза эталон и старт проверяются вручную локальным запуском тестов через `uv run --with numpy pytest labs/<lab-id>`, если pytest подойдёт (уточнится в срезе).

## Шаг 4. Согласование с текстом

- Функции и аргументы в лабе совпадают с текстом главы (раздел «Код»), например `attention(Q, K, V, mask=None)`.
- В тексте главы не копируем решение, только ссылку на шаги лаба.
- Визуализаторы показывают то же, что рисунки главы: веса внимания, форма матриц, распределение по строке. Если в главе есть демо того же, используем общий компонент.
- Лаб не объясняет теорию: это делает глава. В лабе только подсказки на уровне задачи в docstring стартового кода.

## Варианты рантайма

### A. `pyodide-numpy` (по умолчанию для DL и Classic ML)

Работает в браузере через Pyodide в Web Worker с таймаутом (принудительный terminate). Торча в Pyodide нет (проверено 2026-10-16), поэтому все DL-лабы на NumPy. Тесты и эталон выполняются в том же рантайме, что и у читателя.

### B. `simulator` (Compute: память, варпы, коалесцирование)

Лаб на пошаговой модели (JS/TS или Python в Pyodide), без реального GPU. Читатель меняет параметры модели или схему доступа, а тесты проверяют счётчики: число транзакций, попадания в кэш, заполненность варпов. Модель описывается в `labs/<lab-id>/simulator.*` и тестируется как обычный код. Факты о железе, которые модель воспроизводит, имеют источник в главе (`CONTENT-GUIDE`, раздел 9).

### C. `external-notebook` (CUDA, Triton, torch на реальном GPU)

Браузер не запускает ядра. Схема:

1. Генератор создаёт `.ipynb` из `starter.py` (кнопка «Открыть в Colab» или «Kaggle»). Ноутбук содержит тот же стартовый код и инструкцию по импорту результата.
2. Читатель запускает ноутбук у себя (Colab, Kaggle, локально) и сохраняет результат в `LabResult` JSON.
3. На сайте JSON импортируется (кнопка «Импорт результата»), тесты `tests_visible` и `tests_hidden` выполняются над импортированным JSON как над фикстурой, визуализаторы рисуют метрики.

CI проверяет то, что можно проверить без GPU: генератор ноутбука создаёт валидный файл; `fixtures/reference_result.json` (эталонный результат, сгенерированный один раз при запуске эталона) проходит схему `LabResult` и тесты; стартовый JSON-заглушка их не проходит.

Если читателю нужно увидеть цифры, а не менять код, используем предрасчёт: таблица результатов, посчитанная заранее и закоммиченная в `labs/<lab-id>/precomputed/`. Тогда `starter.py` может отсутствовать, а тесты проверяют согласованность таблицы со схемой и с текстом главы. Выбор между вариантами A, B и C (и предрасчётом) подтверждает оркестратор по вопросу 4 плана.

## Шаг 5. Чеклист перед сдачей

- [ ] `lab-id` = `<topic>-<slug>`, совпадает с папкой и с `labs` в frontmatter главы.
- [ ] Все пять файлов на месте (или фикстуры для варианта C).
- [ ] Эталон проходит все тесты; старт падает хотя бы в одном.
- [ ] Тесты детерминированы, допуски явные, сообщения на английском без утечки скрытых значений.
- [ ] Код и комментарии на английском; текст подсказок и пояснений в главе на русском.
- [ ] `lab.yaml` валиден по схеме, `chapter` указывает на существующую главу.
- [ ] Команды шага 3 зелёные; ruff чистый.

## Шаг 6. Слияние и отчёт

- Лаб сливается раньше главы, если глава на него ссылается (`CLAUDE.md`: порядок по зависимостям).
- Коммит: `content(<topic>/<slug>): add lab <lab-id>` или `feat(labs): ...` для рантайма и раннера. Английский, без упоминаний агентов, моделей и ИИ, без `Co-Authored-By`.
- Отчёт lab-author по `tasks/REPORT-TEMPLATE.md`, до 200 слов: файлы, вывод команд `lab-check`, открытые вопросы (например, нужен ли новый разрешённый пакет в Pyodide).
- Удалить `tasks/claims/lab-<lab-id>.claim` и worktree после слияния.
