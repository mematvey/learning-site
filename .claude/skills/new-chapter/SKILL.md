# Процедура: новая глава

Вход: id главы (`<topic>/<slug>`, например `dl/attention`), тема, список лабов (если есть), источники-кандидаты. Правила: `CLAUDE.md` («Общие соглашения»), `docs/CONTENT-GUIDE.md`, `docs/design-system.md`. Процедура выполняется оркестратором. Сам текст не пишет.

Команды ниже (`npm run check`, `npm run build`, `uv run ruff check`, `lab-check`) появятся в вертикальном срезе. До этого критерии приёмки проверяются вручную по чеклисту `docs/CONTENT-GUIDE.md` (раздел 10), а команды в пакете указываются как «когда появятся».

## Шаг 0. Заявка и проверка конфликтов

1. Работа в своём worktree и ветке: `git worktree add -b task/content-<topic>-<slug> .worktrees/content-<topic>-<slug> main`.
2. `git pull`, затем `tasks/claims/`. Если есть заявка на тот же `content/<topic>/<slug>/` или на тот же `id`, работу не начинаем.
3. Создать и запушить `tasks/claims/content-<topic>-<slug>.claim` (одна строка: дата и id). После слияния файл удалить.
4. Проверить `id` и `aliases`: ни одна существующая глава не использует этот `id` или alias.
5. Проверить пререквизиты: все `prereqs` есть в `content/`, иначе либо сначала их делаем, либо помечаем как «будет» и не ссылаемся на них в тексте.
6. Список термов: какие записи глоссария нужны. Новые термы добавляет оркестратор в общий файл глоссария (он не принадлежит пакету главы).

## Шаг 1. Файлы

Создаются:

- `content/<topic>/<slug>/index.svx`: frontmatter по схеме (`docs/CONTENT-GUIDE.md`, раздел 3) и текст по скелету (раздел 4).
- `content/<topic>/<slug>/` для рисунков, которые не делаются демо (если есть, по одному файлу на рисунок).
- `labs/<topic>-<slug>/` для лаба: см. `.claude/skills/new-lab/SKILL.md`. Если лаб не нужен, в `labs` frontmatter список пуст.
- Новые демо-компоненты: в `src/lib/` (точный путь в `docs/ARCHITECTURE.md`), только если статика не передаёт суть (`CONTENT-GUIDE`, раздел 7).

Не трогаем: реестры тем, глав и лабов (генерируются сканированием папок), `CLAUDE.md`, `docs/*`, `src/routes/*`, общий глоссарий, конфиги.

## Шаг 2. Пакеты работ

Каждый пакет по `tasks/TEMPLATE.md` (шаблон появится в срезе; до этого по образцу `tasks/mockup-wave.md`): цель, владеемые и запрещённые файлы, критерии приёмки командами, бюджет (до ~100–140k токенов, до ~600 строк), точное сообщение коммита без упоминаний агентов и моделей.

Нарезка:

| Пакет | Роль | Файлы | Когда |
|---|---|---|---|
| P0 Скелет | architect (или Sonnet medium) | `index.svx`: frontmatter, якоря разделов, пустые `Level` / `Variant` | первым, быстро |
| P1 Демо | component-dev | `src/lib/...` и тесты логики, по одному демо на пакет | параллельно с P3, если демо нужны |
| P2 Текст | content-writer | `index.svx` целиком, один исполнитель | после P0; одна глава = один файл = один исполнитель |
| P3 Лаб | lab-author | `labs/<lab-id>/` | параллельно с P2, по согласованным id блоков и `lab.yaml` |
| P4 Проверка фактов | verifier | только читает; отчёт в `tasks/` | после P2 |
| P5 Визуал | design-qa | только читает; скриншоты | после P1 и P2 |

Правила параллелизма:

- Текст одной главы в один исполнитель. Разделы не пишем параллельно: все пишут в `index.svx`. Если текст большой, исполнитель работает по разделам последовательно в одном запуске (можно продолжить через SendMessage, не начиная заново).
- Id блоков и id лаба фиксируем в P0, до старта P2 и P3. Лаб и текст ссылаются на эти id, а не на придуманные по ходу.
- Verifier не видит процесса написания: запускаем его по готовому файлу в новом контексте.
- Если пакет провален дважды, режем его мельче (по разделу или по одному блоку).

## Шаг 3. Критерии приёмки (командами)

Выполняет оркестратор по каждому пакету, а не верит отчёту:

1. `npm run check`: svelte-check, ESLint, Prettier, Vitest, проверка контента (схема frontmatter, уникальность и формат `{#id}`, покрытие `Variant`, правило «вниз по уровням», существование `prereqs`, `labs`, `concepts`, `supports`). Команда появится в срезе.
2. `npm run build`: страница главы собирается, KaTeX отработал, без ошибок mdsvex.
3. `uv run ruff check` для Python-файлов (лабы и скрипты), если пакет их трогал.
4. Лаб: `lab-check labs/<lab-id>` (эталон проходит, старт падает; см. skill `new-lab`).
5. Ручная проверка по `docs/CONTENT-GUIDE.md`, раздел 10: чеклист пройден, без открытых замечаний verifier.
6. Визуал: `uv run --with playwright python docs/mockups/shoot.py` (или аналог в срезе) для главы в обеих темах, на уровнях c=1/d=1 и c=3/d=3. Оценку даёт design-qa, не автор.
7. Ссылки: все внешние источники открываются, версии документации указаны, поле `accessed` заполнено.

## Шаг 4. Перед слиянием

- Ветка переписана поверх `main` (`git rebase main`), проверки шага 3 повторены после rebase.
- Отчёты субагентов по `tasks/REPORT-TEMPLATE.md`, до 200 слов, без упоминаний агентов в коммитах и PR.
- Порядок слияния: сначала лаб (если эталон не проходит, главу не сливаем), затем глава, затем обновление глоссария.
- Коммит: `content(<topic>/<slug>): <что сделано>` на английском. Пример: `content(dl/attention): add chapter with scaled dot-product`. Без `Co-Authored-By` и без упоминаний ИИ, агентов и моделей.
- Удалить `tasks/claims/content-<topic>-<slug>.claim`, слитые worktree и ветку.

## Шаг 5. Что вернуть пользователю

Коротко: id главы, путь к файлу, результаты команд шага 3 (зелёно или нет), открытые замечания verifier и design-qa, список новых терминов и демо, которые ушли в отдельные пакеты.

## Частые сбои

- Ссылка на термин из более глубокого слоя: переписать на слова или перенести определение выше. Не отключать линтер.
- `Variant` не покрывает значения оси: добавить недостающий вариант.
- Число без источника: удалить или заменить качественной формулировкой.
- Демо без текстовой альтернативы или без «Что заметить»: не сливать, вернуть автору.
- Заметки по главе сиротеют: в главе сменили id блока без `aliases`.
